#25 — Harness Engineering
Type	Classification	Total Score	Confidence	Evidence
Agent runtime / control-plane discipline	Current + Emerging	94	High	[20], [21], [22], [23], [24], [25], [26]
Plain-language definition: Harness Engineering is the design and continuous tuning of the runtime and control environment that surrounds an AI model and turns model capability into dependable agent behavior. A production harness can govern the agent loop, tool execution, sandboxing, permissions and authentication, state persistence, context access, skills, validation, observability, recovery, escalation, and user or agent interfaces. The model supplies probabilistic intelligence; the harness determines what it may access and execute, what controls are enforced mechanically, and how work persists and recovers.
Why it matters to senior leaders: Model choice does not govern an agent by itself. The harness determines practical blast radius, auditability, portability, cost, reliability, and autonomy. OpenAI and Anthropic both treat the surrounding environment and controls as load-bearing for dependable agents. Two 2026 preprints add evidence: harness evolution raised Terminal-Bench 2 pass@1 from 69.7% to 77.0% with cross-model-family gains, while code-owned harness contracts held across 270 runs using three hosted models. Harness design is therefore a strategic architecture and risk decision, not developer plumbing.
Why it matters to knowledge workers: Users experience the harness through available tools, accessible files and systems, permissions, approval gates, retained state, and review evidence. A stronger harness enables longer delegation with clearer boundaries and fewer manual interventions while keeping consequential actions and failures visible for human judgment.
Practical organizational example: A legal-research agent uses only approved repositories, defaults to read-only access, isolates matter state, executes tools in a sandbox, validates cited claims against sources, requires human approval before external communication, and records actions for audit. The underlying model can change without removing these code-owned controls.
Key opportunities: Reliable long-horizon autonomy; reusable tool and permission policies; safer model substitution; centralized guardrails; resumable state; mechanical business rules; observability and debugging; recovery and escalation; lower supervision; and reusable infrastructure that compounds across future runs.
Principal risks or limitations: Over-permissioned tools; weak sandboxing or credential isolation; corrupted state; insufficient logging; brittle scaffolding that becomes obsolete as models improve; provider coupling; complexity, latency, and token cost; conflicting controls; and assuming a harness can make an incapable model reliable.
Common misconception: Harness Engineering is not a prompt template, tool list, or agent framework. It is the executable control environment that makes model decisions operational. The boundary is still settling: some sources use “harness” narrowly for instructions and guardrails, while systems such as Codex use it broadly for the loop, persistence, configuration and authentication, tools, and extensions. This reference uses the broader systems definition.
What to monitor next: Task success by model-plus-harness combination; tool-call safety; least-privilege permissions; sandbox and credential isolation; resume integrity; recovery and escalation; trace completeness; model-substitution evaluations; latency and cost; ablations as models improve; and portable harness interfaces. Evidence: [20], [21], [22], [23], [24], [25], [26].
